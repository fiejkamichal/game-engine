Systemy wieloagentowe, vibe coding, jeden kod — cztery role. Engine gier turowych jako pretekst do mówienia o architekturze AI.

Plan na 90 minut

Agenda

  • ~45 min — Teoria. Czym są i czym nie są systemy wieloagentowe AI. Orkiestracja, kontrakty, skille.
  • ~7 min — Przerwa na kawę. Reset, rozprostowanie nóg, zalogowanie do copilota.
  • ~30 min — Praktyka. Vibe coding na żywym repo. Dopinasz funkcję w ~10 minut, używając darmowego copilota.
  • ~8 min — Q&A. Pytania, kierunki dalszej pracy, materiały.

Wymagania: laptop, internet, darmowe konto AI (np. ChatGPT).

Punkt wyjścia

Vibe coding

Programowanie, w którym opisujesz intencję, a kod pisze maszyna.

Brzmi prosto, dopóki nie spróbujesz. Bo żeby zrobić to dobrze — wiedzieć, co dać AI w kontekst, gdzie postawić granice, kiedy podzielić zadanie — musisz znać warstwy, które są pod spodem.

Przez następne ~25 minut zbudujemy je razem, od dołu do góry.

Warstwa 1 — Model

LLM — funkcja tekst → tekst

Co robi

Bierze tekst na wejściu. Zwraca tekst na wyjściu. Koniec.

Czego NIE robi

  • Nie pamięta nic między wywołaniami
  • Nie ma dostępu do plików, internetu, twojego edytora
  • Nie wie nawet, że gada z tobą — widzi tylko jeden tekst

To wszystko, co siedzi pod ChatGPT, Cursorem, Copilotem. Naprawdę.

Warstwa 2 — Prompt + inferencja

Jedno wywołanie = jeden tekst wejściowy

Co składa się na prompt

  • system — „jesteś asystentem programisty"
  • history — poprzednie wymiany w tej rozmowie
  • user — „napisz funkcję X"

Wszystko sklejone w jeden tekst, do jednego wywołania = jedna inferencja.

Sztywne ograniczenie

Token window — kontekst ma twardy limit (np. 200k tokenów).

Co się nie zmieści — przepada. Stąd cały temat zarządzania kontekstem w warstwie wyżej.

Warstwa 3 — Aplikacja

ChatGPT, Cursor, Copilot to nie LLM-y — to hosty

  • Piszą za ciebie system prompt — nadają osobowość i reguły gry
  • Zarządzają kontekstem — kompakcja długich wątków, retrieval z plików, dobór fragmentów kodu
  • Dają UI — wątki, czat, edytor, terminal
  • Spinają narzędzia — o tym za chwilę

Ten sam LLM w ChatGPT i w Cursorze zachowuje się inaczej — bo aplikacje są różne.

Warstwa 4 — Narzędzia (tools)

Jak LLM coś robi w świecie zewnętrznym

Mechanizm w trzech krokach

  • Aplikacja wystawia LLM-owi listę funkcji (read_file, run_shell, write_file…)
  • LLM w odpowiedzi „prosi" o wywołanie konkretnej funkcji z argumentami
  • Aplikacja wykonuje, wynik wraca do kontekstu jako kolejny element

Jak to wygląda technicznie

{
  "tool": "read_file",
  "args": { "path": "agents/orchestrator.md" }
}

Aplikacja czyta plik, treść wraca do LLM-a, LLM widzi ją w kolejnej inferencji.

Warstwa 5 — Skille

Narzędzia dodawane przez ciebie

Co to jest skill

Proceduralne know-how — „jak zrobić X poprawnie tutaj". Plik markdown w repo. Bez autonomii, bez roli.

Aplikacja-host wstrzykuje skill do kontekstu, kiedy jest potrzebny — technicznie tak samo, jak każde inne narzędzie.

Skille w naszym repo

  • skills/commit-message.md — jak pisać commit
  • skills/file-io-safety.md — atomic write JSON
  • skills/react-board-rendering.md — renderowanie planszy
  • skills/write-adr.md — szablon ADR-a
  • skills/define-typescript-contract.md — dyskryminowane unie i exhaustive switch

Warstwa 6 — Agenci

System prompt dodawany przez ciebie — z rolą i misją

Wzorzec promptu agenta

  • Rola — kim jest, jakie ma kompetencje
  • Misja / cel — co produkuje, na czym polega sukces
  • Zakres — co należy do agenta
  • Granice — czego nie wolno (np. „nie dotyka UI")
  • Kontrakt wyjścia — format, struktura, kryteria akceptacji

Te sekcje znajdziesz w każdym agents/*.md — pokażę na agents/orchestrator.md.

Agent NIE jest

  • Pojedynczym promptem
  • Czat-botem ogólnego przeznaczenia
  • Skillem — używa skilli, nie jest jednym z nich
  • Magią — to po prostu warstwy 1-5 + twój system prompt

Warstwa 7 — Subagenci

Z perspektywy nadrzędnego agenta subagent to kolejne narzędzie

Interfejs jak każdy inny tool

  • Wejście: zadanie (tekst)
  • Wyjście: wynik (tekst, kod, decyzja)
  • W środku: pełen agent z własnym system promptem, własnym oknem kontekstu, własnymi tool calls

Po co

  • Izolacja kontekstu — subagent nie zaśmieca nadrzędnego
  • Specjalizacja — inny system prompt, inne narzędzia
  • Równoległość — kilku subagentów w tym samym czasie

W Cursorze: Task tool — tam tego szukaj.

Warstwa 8 — Orkiestracja

Cztery role, jeden interfejs do człowieka

  • Orchestrator — jedyny rozmówca człowieka. Tłumaczy intencję na zadania, scala wyniki.
  • Architect — kontrakty typów, ADR-y, decyzje strukturalne. Pisze spec, nie kod.
  • Backend Developer — engine, walidacja ruchu, plik stanu, API.
  • Frontend Developer — rendering planszy, klikalność, stan UI.

Każdy zna swoje granice. Ty rozmawiasz tylko z orchestratorem — jeden kanał, nie cztery.

Warstwa 9 — Way of working

Way of working — jak się tym pracuje na co dzień

Jeden prompt do orchestratora po polsku — reszta dzieje się sama.

  • Ty — piszesz intencję po polsku: „dodaj trzecią grę: Othello"
  • Orchestrator — dzieli na zadania, pisze task brief dla Architecta
  • Architect — definiuje kontrakt typów, deleguje implementację
  • Backend + Frontend — piszą równolegle, każdy w swojej domenie, sięgają po skille
  • Orchestrator — scala diffy, pokazuje ci wynik jednym podsumowaniem
  • Ty — review: „OK" albo „popraw X" → kolejna iteracja

Za chwilę zobaczycie tę kompozycję w żywym repo. Potem sami się tym pobawicie.

Implementacja: tic-tac-toe

validateMove(state, move) {
  if (move.kind !== "place")
    return "Unknown move kind.";
  const { row, col } = move.cell;
  if (row < 0 || row >= 3 || col < 0 || col >= 3)
    return "Out of bounds.";
  if (state.board[row][col] !== null)
    return "Already occupied.";
  return null;
}

Część praktyczna — co jest do zrobienia

Wybierz jedno zadanie

Z1 — Licznik ruchów

Na stronie meczu pokaż „Ruch nr 5" — aktualizuje się po każdym kliknięciu.

Dla zielonych z AI copilotem. 5–8 min.

Z2 — Podświetlenie ruchu

Pole, na które padł ostatni ruch, błyska na 1 sek (np. animate-pulse).

Dla początkujących. 5–10 min.

Z3 — Reset matchu

Przycisk „Nowy mecz tej samej gry" — POST do /api/matches + redirect.

Średnio-zaawansowane. 8–12 min.

Z4 — Statystyka wyników

Na stronie głównej liczniki: ile białych / czarnych / remisów. Czytaj data/matches/.

Średnio-zaawansowane. 10–15 min.

Z5 — Trzecia gra (Othello)

Nowy folder packages/games/othello-mini/ — bez tykania packages/engine/.

Trudne. 15–20 min. Sygnał: nie musisz zmieniać enginu.

Twój pomysł

Coś własnego — ale trzymaj się skali ~10 min i zasad z następnego slajdu.

Na własne ryzyko. Możesz utknąć.

Część praktyczna — jak to zrobić

Vibe Coding — instrukcja

1. Sklonuj repo i odpal lokalnie

git clone https://github.com/fiejkamichal/game-engine.git
cd game-engine
npm install
npm run dev

Otwórz http://localhost:3000 — strona z listą gier.

2. Otwórz copilota AI

  • GitHub Copilot Chat w VS Code / Cursor (jeśli masz licencję).
  • Albo darmowy chat w przeglądarce: chatgpt.com, claude.ai, gemini.google.com.

Wszystko jedno który — ten warsztat o to jak, nie czym.

3a. Z copilotem — użyj orchestratora

  • Opisz orchestratorowi po polsku co ma zrobić — nie jak.
  • Prześledź odpowiedź. Upewnij się, że delegował robotę do subagentów (Architect, Backend, Frontend), zamiast pisać wszystko sam.
  • Iteruj — krótkie cykle, „popraw X", „dorzuć Y".

3b. Bez copilota — alternatywa

  • Wklej do darmowego chata kontekst ręcznie: agents/*.md, odpowiedni GameDefinition, fragment komponentu UI.
  • Potem opisz zadanie. Krótkie cykle, nie jeden mega-prompt.

Brakuje ci tooli i subagentów — ale wzorzec ten sam.

Twoje zadanie

Kryteria sukcesu

  • Funkcja działa po odświeżeniu strony.
  • Stan zapisuje się do pliku data/matches/<id>.json — otwórz i sprawdź.
  • Nie psujesz drugiej gry (tic-tac-toe ↔ warcaby działają niezależnie).
  • Jeden commit, conventional commits (feat:, fix:, refactor:).

Bonus: dorzucasz krótkie ADR-ko w docs/architecture/, jeżeli decyzja jest nietrywialna.

Q&A

Pytania?

Eksperymenty, kierunki rozwoju, „czy mogę zrobić X”.

Materiały zostają w repo — możesz wracać.

A jeśli macie chwilę — wypełnijcie krótką ankietę po warsztacie. Zajmie 2 minuty, a mnie pomoże ulepszyć kolejne edycje.
